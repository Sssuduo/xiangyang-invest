## 1. 背景与问题

### 1.1 当前实现（与代码核对一致）

```python
CHUNK_SIZE = 50000          # 摘要阶段单段输入上限（字符）
ECHO_CHUNK_SIZE = 2000      # 发言分段/清洁版单块字符数（回写阶段）
ECHO_MAX_TOKENS = 6000      # 回写阶段单块输出 token 上限
```

三阶段流水线（`text_summarizer.py`）：

- `segment_meeting`（阶段1，93:140）：识别发言轮次、插入 `[发言N]:` 标记，**100% 保留原文**，仅做切断。
- `clean_meeting`（阶段2，143:189）：在分段基础上整理措辞、剔除语气词，**保留全部实质性内容**。
- `summarize_meeting_inner`（阶段3，192:225）：基于清洁版 + 发言分段生成结构化摘要；超长时由 `_merge_summaries`（303:317）先分块总结再合并。

阶段 1/2 的关键安全网（131:132、180:181）：回写结果明显短于原文（被 `max_tokens` 截断）时，**退回原始文本**，保证不丢内容。

### 1.2 真正的问题（修订后的判断）

| 问题 | 根因 | 严重度 |
|---|---|---|
| 阶段 1/2 分块偏小，调用次数多 | 回写型任务必须把整块原文重新输出，块大小受**模型输出 token 上限**约束，不能盲目增大 | 🔴 高 |
| 固定字符数切分 | 可能在句子/段落中间切断（但现有 `_chunk_text` 已按段落/句末切分，属"语义感知"，此问题当前较轻） | 🟢 低 |
| `CHUNK_SIZE = 50000` 固定 | 阶段3 摘要输入可能超过小上下文模型的窗口，导致 API 拒收/截断 | 🟡 中 |
| 块间无重叠 | 摘要阶段跨块时上下文易断裂 | 🟡 中 |

> ⚠️ **初版核心误判**：把"分块大小"当作输入上下文窗口问题，建议 `ECHO_CHUNK_SIZE` 直接提到 8000。但阶段 1/2 是回写任务——8000 中文字 ≈ 12000–24000 输出 token，而常见模型输出上限仅 4096–8192 token，**输出塞不下 → 触发安全网退回原文 → 分段功能反而退化**。因此阶段 1/2 的块大小天花板由"输出 token 上限"决定，而非输入窗口。

### 1.3 量化影响（修正后，基于真实字符数）

以中文会议录音约 **200–300 字/分钟** 计：1 小时 ≈ 12000–18000 字符（初版"6000 字符"偏低，已修正）。

| 指标 | 当前（2000 字符/输出~6000tok） | 修订后（模型感知，大上下文模型≈3000、小上下文≈1700） | 改善 |
|---|---|---|---|
| 阶段1/2 单块字符 | 2000 | 1700（8K 模型）/ 3000（大上下文模型） | 大模型 ↓约 33% 块数 |
| 阶段1+2 调用次数（1.5h≈20000 字） | ~20 次 | ~14 次（大模型） | ↓约 30% |
| 阶段3 跨块连贯 | 无重叠，易断 | 块间 1000 字重叠（句边界对齐） | 质量↑ |
| API 成本 | 高 | 略降（主要省阶段3 重复理解 + 阶段1/2 块数） | ↓约 20–30% |

> 阶段 1/2 的降本空间受回写约束天然有限；**真正可放心放大块、降成本的是阶段 3（输出短、不受回写约束）**，以及避免小上下文模型因 `CHUNK_SIZE=50000` 超限。

## 2. 设计目标

1. **不破坏回写安全网**：阶段 1/2 块大小必须保证模型能把整块原文完整输出（受输出 token 限制）。
2. **模型感知**：分块大小按模型上下文窗口 + 输出能力动态计算，而非硬编码。
3. **语义完整**：切分点优先段落边界、句末标点（现有 `_chunk_text` 已满足）。
4. **跨块连贯（仅摘要阶段）**：阶段 3 块间保留重叠区；阶段 1/2 **不加重叠**（独立回写会致内容重复）。
5. **向后兼容**：不改变对外函数签名与返回格式。

## 3. 方案：模型感知分块 + 阶段3重叠

### 3.1 核心参数（修订）

```python
ECHO_CHUNK_SIZE = 2000        # 回写阶段块大小基线（动态计算下限参考）
ECHO_MAX_TOKENS = 6000        # 回写阶段输出上限基线
ECHO_CHUNK_SIZE_MAX = 3000    # 回写阶段块大小硬上限（受输出 token ~8K 限制，2*3000=6000≤常见上限）
ECHO_OVERLAP_CHARS = 0        # 回写阶段不加重叠（避免独立回写内容重复）

SUMMARY_CHUNK_CHARS = 30000   # 摘要阶段块大小上限
SUMMARY_OVERLAP_CHARS = 1000  # 摘要阶段块间重叠（句边界对齐）
```

### 3.2 模型感知分块大小

新增启发式（依据 `model_name`/`provider` 关键字估算上下文窗口，未知取保守 8000）：

```python
def _model_context_window(config): ...   # 8K/32K/128K 等 → 返回 token 数，未知 8000

def _echo_chunk_params(config):
    """回写阶段 (阶段1/2)：块大小受输出 token 约束。
    C 字符块 → 输出 ~2*C token，输入 ~1.5*C token；合计 ≤ 上下文 * 0.75。
    输出上限硬控 8192。返回 (chunk_chars, max_tokens)。"""
    ctx = _model_context_window(config)
    c = ctx * 0.75 / 3.5                      # 3.5 ≈ 1.5(输入)+2(输出)
    chunk_chars = int(min(ECHO_CHUNK_SIZE_MAX, max(1000, c)))
    max_tokens = int(min(chunk_chars * 2.2, 8192))
    return chunk_chars, max_tokens

def _summary_chunk_chars(config):
    """摘要阶段 (阶段3)：输出短，受输入上下文约束。"""
    ctx = _model_context_window(config)
    return int(min(SUMMARY_CHUNK_CHARS, max(2000, ctx * 0.7 / 1.5)))
```

效果：8K 模型阶段1/2 保持 ~1700（不劣于现状）；32K/128K 模型提到 ~3000（省约 1/3 调用）；阶段3 软上限按上下文收敛，避免小模型超限。

### 3.4 重叠适用范围（关键修订）

- **阶段 3（摘要）**：重叠安全且有益。每块独立"理解/总结"（非逐字回写），重叠仅丰富输入上下文；最终由 `_merge_summaries` 去重合并。故阶段3 使用 `overlap=SUMMARY_OVERLAP_CHARS`。
- **阶段 1/2（回写）**：**不使用重叠**（`ECHO_OVERLAP_CHARS=0`）。因每块独立回写后直接拼接（`'\n\n'.join`），若输入带重叠，重叠文本会在"前块末尾 + 后块开头"各出现一次 → 内容重复。初版在此处的去重描述不足以覆盖回写阶段，故直接禁用。

### 3.5 与现有实现的关系（避免重复造轮子）

- **阶段 3 层级合并已存在**：`_merge_summaries`（303:317）已实现"分块总结→合并→仍超长再分块→退化拼接防死循环"。本方案**复用**，仅在分块时增加重叠，不重写合并逻辑。
- **语义切分已存在**：原 `_chunk_text`（236:263）已按段落/句末切分；本方案仅追加 `overlap` 参数，未改变切分语义。
- **函数签名不变**：`segment_meeting` / `clean_meeting` / `summarize_meeting` 签名与返回格式不变，调用方无感。

## 4. 备选方案对比（修订）

| 方案 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|
| **A. 固定增大 (如 8000)** | 改动最小 | 回写型任务输出塞不下 → 触发退回原文兜底，分段退化 | ⭐（不采用） |
| **B. 模型感知分块 + 阶段3重叠（采用）** | 安全、不破坏回写、省调用、跨块连贯 | 需维护上下文启发式表 | ⭐⭐⭐⭐⭐ |
| **C. 按议题/章节切分** | 每块语义最完整 | 需先识别议题，额外 LLM 调用 | ⭐⭐⭐⭐（未来） |
