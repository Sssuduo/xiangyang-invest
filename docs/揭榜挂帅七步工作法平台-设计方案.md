# 揭榜挂帅七步工作法平台 — 设计方案

> 配合"揭榜挂帅"项目，在襄阳农高区招商平台内建设**线上技术对接平台**，
> 建立"**需求征集 → 专家论证 → 发榜公告 → 揭榜评审 → 任务签订 → 过程管理 → 绩效评价**"七步工作法，
> 实现从企业技术需求到项目结题的**全周期线上化服务跟踪**。
>
> 版本：v2（双端口架构）｜适用代码基线：master 8d74720（V16.25+）

## 〇、参考研究结论（外部平台对标）

设计前调研了各地揭榜挂帅实施规范与同类线上平台，核心参考：

- **[赣州市"揭榜挂帅"制项目管理工作实施细则](https://www.ganzhou.gov.cn/zfxxgk/c143699/202507/2a32678165124743b7d2ae3d99ee7c6a.shtml)**：需求征集→论证→发榜→揭榜→评审→签约→管理→验收的官方流程骨架，与本项目七步工作法一致；
- **[广西科技计划"揭榜挂帅"项目管理办法](http://gioar.cn/article/338)**：明确揭榜方资质条件、任务书要点、过程检查与绩效评价要求；
- **公务员报名系统模式**：公开注册→邮箱回执→登录→提交材料→审核→查询进展，是"对外端口"交互的成熟范式。

对标结论（本方案遵循）：
1. 对外端口**注册即邮箱回执**、申请提交即回执，且揭榜方可随时查询自身项目进展——**知情权**是这类平台的信任基础；
2. 内部端口对**外部提交全量可见、可操作、可审核**，且可同时**内部代为录入**（专班掌握的企业需求/揭榜信息）；
3. 评审、定标、任务书、里程碑、绩效评价等专业动作**只发生在内部端口**，对外端口仅展示结果与状态。

## 一、业务背景与目标

### 1.1 揭榜挂帅机制说明

揭榜挂帅是科技攻关组织管理的新机制：**由企业"出题"**（技术需求），**政府/园区平台"发榜"**，**高校、科研院所、企业团队"揭榜"**，通过评审择优确定揭榜方，签订任务书后实施攻关，最终按绩效评价成果。其核心价值是让技术需求与创新供给精准对接。

### 1.2 七步工作法（本系统的业务流程骨架）

| 步骤 | 名称 | 业务含义 | 本阶段关键动作 |
|---|---|---|---|
| 1 | 需求征集 | 征集企业/产业技术需求 | 需求登记（企业、技术描述、预期投入、时限） |
| 2 | 专家论证 | 论证需求是否适合揭榜挂帅 | 专家名单、论证意见、通过/驳回 |
| 3 | 发榜公告 | 公开发布榜单 | 悬赏金额、揭榜条件、截止时间、发布 |
| 4 | 揭榜评审 | 接收揭榜申请并择优 | 申请登记、评分、评审结论、定标/流标 |
| 5 | 任务签订 | 签订攻关任务书 | 任务经费、期限、里程碑计划 |
| 6 | 过程管理 | 实施期跟踪服务 | 进展记录、里程碑核查、问题协调 |
| 7 | 绩效评价 | 结题评价与成果跟踪 | 评分定级、评价报告 |

> 另有三个**终止态**：论证驳回（`rejected`）、流标（`failed`）、终止/取消（`cancelled`）。

### 1.3 平台目标

1. 一个榜单**贯穿七个阶段**，任何时刻可看到"现在走到哪一步、下一步该干什么"；
2. 每个阶段有**规范的状态与操作**，后端强制流转顺序，杜绝跳步；
3. **全周期服务跟踪**：任一阶段的操作/服务/进展都写入时间线，形成项目全生命周期档案；
4. 与现有平台一致的用户体验：复用字典、看板、权限、审计模式。

### 2.1 双端口职责划分

| 能力 | 对外端口（揭榜方） | 内部端口（专班） |
|---|---|---|
| 需求征集登记 | — | ✅ 录入/编辑/附件 |
| 专家论证（名单/意见/通过/驳回） | 仅见结论（如驳回原因） | ✅ 全操作 |
| 发榜公告 | ✅ 浏览已发布榜单（匿名） | ✅ 发布/截止 |
| 揭榜申请 | ✅ 登录后提交（自动邮箱回执） | ✅ 全量查看 + 内部代录 |
| 揭榜评审/定标/流标 | 仅见结果（中标/未中标） | ✅ 评分/评审/定标 |
| 任务签订/里程碑 | 仅见任务书要点与里程碑状态 | ✅ 全操作 |
| 过程管理 | ✅ 查看自身项目进展（时间线/里程碑） | ✅ 记录进展/核查里程碑 |
| 绩效评价 | 仅见评价结果与等级 | ✅ 评分定级 |
| 注册/信息维护 | ✅（邮箱回执） | 审核/禁用用户 |

### 2.2 设计原则

1. **一条记录贯穿七步**：不按阶段建多个主表，主表 `bidding_projects.current_stage` 标记当前阶段，各阶段专属字段（论证意见、发布时间、绩效等）为可空列，避免表爆炸；
2. **状态机收敛在后端**：前端只是"按钮 + 表单"，阶段流转合法性由 `services/bidding_service.py` 统一校验；
3. **时间线即档案**：所有阶段操作自动写 `bidding_timeline`（system 类型），人工服务记录写 service 类型——"全周期服务跟踪"由这一张表完整承载；
4. **信息隔离**：对外端口只能看到**已发布榜单**与**本人提交的申请/项目**；内部端口全量可见；
5. **复用而非发明**：字典（仿 `ConstructionProjectTypeDict`）、列表/详情（仿 `admin_construction.py`）、看板（仿 `DashboardView` 超期表格）、权限（`dual_login_required` + `visitor_block`）、审计（`log_changes`）。

## 四、状态机设计（services/bidding_service.py）

```
stage1 需求征集 ──提交论证──▶ stage2 专家论证 ──通过──▶ stage3 发榜公告
                                        │驳回            │发布+到期
                                        ▼                ▼
                                  rejected(终止)      stage4 揭榜评审 ──定标──▶ stage5 任务签订 ──签订──▶ stage6 过程管理
                                        ▲                │流标               │
                                        └────── cancelled◀┘终止              ▼
                                                                   stage7 绩效评价 ──评价──▶（终态，可改）
```

**流转接口**：`POST /bidding/projects/<id>/transition`，`body = {action, ...payload}`。

| action | 前置阶段 | 说明 |
|---|---|---|
| submit_argument | stage1 | 提交论证 → stage2 |
| argument_pass | stage2 | 论证通过 → stage3（写论证意见/专家） |
| argument_reject | stage2 | 论证驳回 → rejected（终止态） |
| publish | stage3 | 发布公告（写悬赏/截止/条件） |
| expire | stage3 | 截止揭榜 → stage4 |
| select_bid | stage4 | 定标（选揭榜申请）→ stage5 |
| fail_bid | stage4 | 流标 → failed（终止态） |
| sign | stage5 | 签订任务书（写任务信息）→ stage6 |
| complete | stage6 | 实施完成 → stage7 |
| terminate | stage6 | 终止 → cancelled |
| evaluate | stage7 | 提交绩效评价（可重复修改） |
| cancel | 任意（除终态） | 项目取消 → cancelled |

**规则**：每步 action 只允许在指定阶段调用，非法流转返回 400 并给出中文提示；每次成功流转自动写一条 system 时间线记录。

## 五、后端 API 设计

### 5.1 内部端口（routes/admin_bidding.py，`/api/admin/bidding/*`）

```
GET    /bidding/dicts                        # 领域字典 + 阶段定义 + 状态选项
GET    /bidding/projects                     # 列表（搜索/阶段/领域筛选 + 分页）
POST   /bidding/projects                     # 新建（需求征集登记）
GET    /bidding/projects/<id>                # 详情（含子表数据）
PUT    /bidding/projects/<id>                # 编辑（各阶段通用信息）
DELETE /bidding/projects/<id>                # 删除（软删）
POST   /bidding/projects/<id>/transition     # 阶段流转（见状态机）
# 揭榜申请（内部全量管理 + 代录）
POST   /bidding/projects/<id>/bids           # 登记揭榜申请（内部代录）
PUT    /bidding/projects/<id>/bids/<bid_id>  # 编辑申请/评分
DELETE /bidding/projects/<id>/bids/<bid_id>  # 删除申请
# 里程碑
POST   /bidding/projects/<id>/milestones            # 新增里程碑
PUT    /bidding/projects/<id>/milestones/<mid>      # 编辑
DELETE /bidding/projects/<id>/milestones/<mid>      # 删除
POST   /bidding/projects/<id>/milestones/<mid>/status  # 更新完成状态（过程管理核查）
# 全周期服务跟踪
POST   /bidding/projects/<id>/timeline       # 追加服务/跟踪记录（人工）
DELETE /bidding/projects/<id>/timeline/<tid> # 删除记录
# 揭榜方用户管理
GET    /bidding/users                        # 揭榜方用户列表（注册来源、状态）
PUT    /bidding/users/<id>                   # 启用/禁用
# 看板
GET    /bidding/stats                        # 七步漏斗统计 + 超期榜单
```

权限：全部 `@dual_login_required`；写操作叠 `@visitor_block`；变更写 `log_changes` 审计。

### 5.2 对外端口（routes/bidding_public.py，`/api/bidding/*`）

```
POST   /register                # 揭榜方注册（生成账号，异步发邮箱回执）
POST   /login                   # 揭榜方登录（session: bidding_user_id）
POST   /logout
GET    /me                      # 当前揭榜方信息
PUT    /me                      # 维护基本信息（单位/联系人/电话/密码）
GET    /boards                  # 公开榜单列表（仅已发布且未截止，匿名单栏+已登录标记）
GET    /boards/<id>             # 榜单详情（需求描述/悬赏/揭榜条件；已登录可申请）
POST   /boards/<id>/apply       # 提交揭榜申请（异步发邮箱回执；每人每榜限一条有效申请）
GET    /my-applications         # 我的申请列表（状态：评审中/中标/未中标）
GET    /my-applications/<id>    # 我的申请详情（中标后可见：任务书要点/里程碑/时间线/绩效结果）
```

鉴权：公开路由匿名可访问；`/me`、`apply`、`my-applications` 需揭榜方登录（session）。**信息隔离**：`my-applications` 仅返回本人数据；内部提交的申请（user_id 为空）不会出现在任何揭榜方账号下。

### 5.3 邮件服务（services/email_service.py）

| 项 | 设计 |
|---|---|
| 发送方式 | `smtplib`，支持 SSL(465) / STARTTLS(587)，配置来自环境变量（config） |
| 异步 | 线程池后台发送，不阻塞 HTTP 请求 |
| 降级 | SMTP 未配置或发送失败 → 记日志（错误不阻断业务，界面提示"已提交，回执邮件如未收到请联系专班"） |
| 模板 | 注册回执（含账号与登录提示）、揭榜申请回执（含申请单号/内容摘要/后续流程说明） |

配置项（`backend/.env` 生产注入）：
```
SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASSWORD / SMTP_FROM
```

## 六、前端页面设计

### 6.1 `BiddingPortal.vue`（对外门户 `/bidding-portal` — 揭榜方端口）

独立布局（无业务导航，顶部为门户导航：首页/揭榜挂帅/联系我们），包含：

- **榜单浏览**（匿名可看）：卡片/列表展示已发布且在揭榜期的榜单（名称、领域、发榜企业、悬赏、截止日）；
- **榜单详情**：技术需求描述、揭榜条件、悬赏金额；已登录揭榜方显示"提交揭榜申请"入口（表单：技术方案/团队优势/报价）；
- **注册/登录**：弹窗表单（单位信息+邮箱+密码），注册成功提示"回执邮件已发送"；登录后右上角显示用户菜单；
- **个人中心**：
  - 基本信息维护（单位、联系人、电话、改密码）；
  - **我的申请**：申请列表（状态 tag：评审中/中标/未中标）+ 申请详情；
  - **项目进展**：中标后展示项目七步当前阶段、任务书要点、里程碑核查表（状态着色）、全周期时间线（仅展示已发生的流转与人工服务记录）、绩效评价结果——**揭榜方可实时查看自身项目推进情况**。

### 6.2 `BiddingView.vue`（业务端主视图 `/bidding`）

- 顶部 `BusinessNavbar`（新增"揭榜挂帅"下拉菜单：平台管理 / 数据看板）；
- **列表区**：搜索（名称/企业）、按阶段筛选（七步 tag 下拉）、按领域筛选、添加需求按钮；表格列：序号、榜单名称、发榜企业、技术领域、当前阶段（el-tag 按阶段着色）、悬赏金额、截止日期、更新时间、操作（详情/编辑/删除）；
- **详情抽屉**：
  - 顶部 `el-steps` 七步流程条，当前阶段高亮，终止态红显；
  - 各阶段信息卡片（论证意见、公告信息、揭榜申请列表（标注外部提交/内部代录）、里程碑、时间线）；
  - 操作区只渲染**当前阶段**的可用动作（提交论证/论证通过|驳回/发布|截止/定标|流标/签订/完成|终止/绩效评价）；
  - **全周期时间线**：倒序展示所有跟踪记录（自动流转记录 + 人工服务记录），可随时追加服务记录——"全周期服务跟踪"的落点。

### 上线前配置提醒

1. **SMTP 邮件**：生产 `backend/.env` 需配置 `SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASSWORD / SMTP_FROM`，否则注册/申请回执邮件仅记日志不发送（业务不阻断）；
2. **数据库**：重启后端自动 `db.create_all()` 建 6 张新表并 seed 领域字典，无需手工迁移；
3. **部署**：按 AGENTS.md 流程从 `dev` 分支合并发布（`deploy.sh` 会自动构建前端并重启）。
